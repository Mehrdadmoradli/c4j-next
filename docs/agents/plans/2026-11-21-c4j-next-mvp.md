# PLAN: C4J Next Java 25 Research Prototype

Build a tested Java 25 Design by Contract framework with Byte Buddy. Reuse and adapt `dbcagent` implementation as a reference, and reproduce the supplied C4J implementation's observable behavior for the supported feature set. Deliver small, buildable increments suitable for review and individual commits.

The implementation budget is four weeks at two development days per week. Phases 1–7 are ordered by thesis priority. Phases 8–9 are a backlog and must not reduce the time available to stabilize, measure, and document earlier phases.

## Acceptance Criteria

- [ ] A clean Java 25 build produces a shaded `c4j-next` Java agent whose manifest names `io.github.Mehrdadmoradli.c4jnext.agent.C4JNextAgent`.
- [ ] Applications use the public package `io.github.Mehrdadmoradli.c4jnext` and C4J-style contract classes, `@ContractReference`, `@Target`, `@ClassInvariant`, and `Condition` helpers.
- [ ] Preconditions execute before the target method and prevent its body from running when C4J would reject the call.
- [ ] Postconditions execute after normal completion for primitive, reference, `null`, and `void` results, with `result()` exposing the same value C4J exposes.
- [ ] Class invariants execute at C4J-compatible method boundaries and only after successful completion of the relevant constructor.
- [ ] Contract violations identify the precondition, postcondition, invariant, or initializer phase and preserve the assertion message, cause, and useful contract stack frames.
- [ ] Every advice exit path restores runtime state after valid calls, contract violations, reflection failures, and application exceptions.
- [ ] Nested calls, recursion, and calls on separate threads retain independent invocation state.
- [ ] `old(expression)` supports a documented subset, captures each supported expression before target execution, and uses a stack per nested invocation.
- [ ] Superclass and interface contracts are discovered in the same order as the supplied C4J implementation for the tested hierarchies.
- [ ] Multiple applicable contracts reproduce C4J's precondition-result handling, postcondition composition, invariant composition, and explicit LSP-violation behavior.
- [ ] `unchanged()` and exceptional-execution helpers are implemented only after the mandatory and high-priority gates are stable.
- [ ] Each optional feature is reported as implemented, partial, unsupported, or not tested based on its own automated evidence.
- [ ] The feature matrix never counts an unsupported or untested C4J behavior as passing.
- [ ] Each phase ends with a passing build, focused automated tests, updated documentation, and a reviewable diff suitable for one commit.

## Technical Key Decisions and Tradeoffs

1. **Behavioral compatibility:** Reproduce the supplied C4J behavior for supported cases, including its contract ordering and LSP handling.
   - Why: The project will be evaluated by functional coverage against C4J.
   - Impact: C4J source and executable fixtures, where runnable, are the behavioral oracle. Differences are explicit compatibility findings rather than silent improvements.

2. **Public API namespace:** Use `io.github.Mehrdadmoradli.c4jnext` while retaining C4J's API shape.
   - Why: This identifies the framework as a new implementation while keeping contract migration understandable.
   - Impact: The artifact becomes `c4j-next`; annotations, `Condition`, and contract errors move under the new namespace.

3. **Implementation foundation:** Copy and adapt the relevant `dbcagent` code with attribution, then replace its fragile runtime state and first-match discovery.
   - Why: Its Byte Buddy agent, matchers, advice, and target injection already establish the intended implementation approach.
   - Impact: Reference directories remain unchanged. Production code receives new package names, tests, and C4J-compatible behavior.

4. **C4J-style contract classes:** Do not expose `dbcagent`'s `ContractBase` as the contract authoring API.
   - Why: C4J contract methods use static `Condition` helpers and contract types that extend or implement the target type.
   - Impact: `Condition.preCondition()`, `postCondition()`, `result()`, `old()`, and later helpers delegate to the current runtime context.

5. **Invocation state model:** Store one `Deque<InvocationContext>` per thread.
   - Why: Independent thread locals lose outer state during nesting and remain dirty after exceptional paths.
   - Impact: Advice pushes one context at entry, operates on the top frame, and pops it in guaranteed cleanup. Frames hold phase, target, method, result, throwable, contract instances, old values, and construction state.

6. **Instrumentation level:** Prefer `AgentBuilder`, matchers, and `Advice`; add a focused bytecode visitor only for behavior that advice cannot express.
   - Why: Method advice covers boundaries cleanly, while C4J-compatible `old(expression)` requires identifying individual call sites and capturing their expressions before target execution.
   - Impact: The `old()` phase includes a dedicated contract-expression transformation with stable expression identifiers.

7. **Test architecture:** Use unit tests for pure runtime/discovery logic and forked-JVM integration tests for the packaged agent.
   - Why: Agent behavior, assertions, class loading, constructor advice, and application exception propagation cannot be established reliably in an in-process unit test alone.
   - Impact: Maven packages the agent before integration tests and runs each isolation-sensitive scenario in a fresh JVM.

8. **Time gate:** Protect mandatory behavior before medium and optional features.
   - Why: Eight implementation days do not provide a reliable estimate for all twenty features.
   - Impact: Phase 7 is the planned thesis freeze. Phases 8–9 proceed only when earlier acceptance checks pass and time remains.

The root artifact and source package use the final C4J Next naming. The supplied `dbcagent` has no tests and currently selects one contract. Its context cleanup can be skipped after a violation, recursive calls overwrite outer state, mutable snapshots alias the target state, exceptional exits can replace the application throwable, and `@Pure` does not enforce purity. The baseline characterization recorded 10 passing and 7 failing scenarios on Java 25.

The supplied C4J code discovers the affected type, superclasses, and interfaces, then gathers every registered contract in its defined order. It separately records precondition successes and failures, reports differing inherited precondition results as an LSP violation, executes applicable postconditions, and stores `old()` values in a per-thread stack keyed by contract expression.

  - Living support matrix with implemented, failing, partial, unsupported, not applicable, and not tested statuses.

## Logging & Observability

Routine contract checks remain silent. Transformation failures report the target class, contract class, method signature, class loader, and root cause. A contract violation message follows C4J's phase terminology, for example `balance must remain non-negative (class-invariant)`, while preserving the original assertion stack trace. Optional debug logging may list resolved contracts and their order, but tests must assert exceptions and state rather than log text.

Phase 4 verified on 2026-11-22 with Java 25. The implementation and verification took a few minutes. Ran `mvn -o -Dmaven.repo.local=<existing cache> clean verify` in a temporary source copy. The final Maven run took about 12 seconds and passed all four packaged-agent integration tests.

Updated `InvocationContext` and `ContractRuntime` to keep the application method and completion outcome in the active frame. Normal completion records the return value and allows postconditions. Exceptional completion records the original throwable and clears the frame without exposing the advice default return value. An instrumented call from an application body can push its own frame. A call made while a precondition, postcondition, or invariant is running executes its body under the existing frame with contract evaluation suppressed, including calls on another receiver.

`InvocationIsolationIT` verifies frame identity and restoration across nested and recursive calls, cleanup after assertion and reflection failures, deterministic overlap on separate and shared receivers, and preservation of application throwable identity, message, suppressed exceptions, and stack frames. The original baseline nested and thread probes also exercise snapshots. Those snapshot assertions remain Phase 5 work. The support matrix records cleanup separately from exceptional contract helpers.
